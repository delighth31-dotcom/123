Контекст проекта: Cloudflow, Camoufox Runtime, OmniRoute и Duck.ai
1. Главная цель
Строим чистую, расширяемую платформу для работы с веб-моделями через единый OpenAI-совместимый интерфейс OmniRoute.
Целевая цепочка:
VS Code / OmniCopilot
        |
        v
OmniRoute
  - единый API-контракт
  - маршрутизация моделей
  - tool emulation
  - преобразование ответов и вызовов
        |
        v
Адаптер конкретной модели/сайта
  - duckai-v1
  - duckai-v2
  - gemini-web
  - glm-web
  - другие адаптеры

        +--------------------+
        |                    |
        v                    v
Browser Runtime        HTTP Transport
Camoufox               fetch / undici
        |                    |
        +---------+----------+
                  |
                  v
           Веб-сервис модели


Главное архитектурное решение уже согласовано:
OmniRoute остаётся API gateway и оркестратором; браузерная инфраструктура становится общей; адаптеры реализуют протоколы конкретных сайтов, не дублируя оркестрацию инструментов.
Мы не хотим переписывать duckai2api целиком, механически раскладывать его по директориям или использовать нынешний код как эталон. Старые проекты — источники уже полученных знаний, работающих алгоритмов и тестовых примеров. В новую систему нужно переносить только то, что обоснованно необходимо.
2. Права и обязанности компонентов
OmniCopilot
Остаётся средой агента в VS Code. Получает структурированные вызовы инструментов от OmniRoute, исполняет разрешённые инструменты — терминал, работа с файлами и прочие средства разработки — и передаёт результаты обратно.
Контракт OmniCopilot менять не следует ради поддержки особенностей какого-либо сайта.
OmniRoute
Единственный владелец обработки tool emulation.
В используемой нами реализации OmniRoute уже есть преобразователь для веб-провайдеров без нативного function calling. Он формирует инструкции для модели и преобразует текстовые конструкции вызовов в OpenAI-совместимые tool_calls.
Исходники и контекст:
- C:\Users\asali\OmniRoute-src\open-sse\translator\webTools.ts
- C:\Users\asali\OmniRoute-src\open-sse\executors\default.ts
- C:\Users\asali\OmniRoute-src\src\app\api\v1\models\catalog.ts
В ветке release/v3.8.52 каталог web-cookie-провайдеров содержит режим toolCalling: "emulated" для ряда веб-моделей. Мы также проверяли непосредственно преобразование ответа DuckAPI в tool_calls.
Подтверждено: механизм эмуляции и ряд связанных unit-тестов работали отдельно.
Не подтверждено: полный цикл, в котором вызов инструмента из реального OmniCopilot исполняется в VS Code, результат возвращается модели и получается корректный итоговый ответ.
Адаптеры моделей
Должны описывать протокол сайта, не реализуя второй самостоятельный агентный фреймворк.
Адаптер отвечает за:
- формат запросов и ответов конкретного сайта;
- заголовки, токены, cookies и идентификаторы диалогов;
- специфические переходы между состояниями;
- восстановление при ошибках upstream;
- выбор браузерного или HTTP-транспорта;
- передачу ответа в общей согласованной форме.
Адаптер не должен самостоятельно исполнять инструменты OmniCopilot или дублировать механизм преобразования tool envelope в tool_calls.
Если протокол сильно изменился, можно создать duckai-v2, оставить старую реализацию и переключать конфигурацию на нужную версию.
3. Общая браузерная инфраструктура
Пока мы не выбрали окончательный движок и не должны заранее переносить браузерный код из duckai2api.
Нам необходимы общие сервисы с чёткими границами:
Browser Runtime: запуск и управление браузерными процессами, контекстами и страницами; распределение сессий; восстановление после отказов.
Session Manager / State Store: хранение состояния, идентификаторов, TTL, синхронизация параллельных операций и восстановление.
HTTP Transport: прямые HTTP-запросы, пулы соединений, таймауты, заголовки, управление TLS-профилями.
Telemetry & Diagnostics: корреляционные ID, события браузера, ошибки, длительность запросов, причины повторов и переходы состояний. Cookies, токены и секреты не должны попадать в обычные логи.
Adapter Host: загрузка адаптера, доступ к общим сервисам и контроль совместимости.
На первом этапе эти модули могут быть частями одного процесса и контейнера. Не нужно заранее создавать множество микросервисов.
Критическое требование изоляции
Под изоляцией пользователь понимает прежде всего независимость состояния разных сессий, а не обязательный отдельный процесс ОС для каждого пользователя.
Нужно гарантировать, насколько это позволяет выбранная технология, что сессия не получает случайно состояние другой сессии:
- cookies и аутентификация;
- localStorage, sessionStorage, IndexedDB;
- service workers и относящееся к контексту состояние;
- параметры браузерной идентичности;
- proxy и сетевая конфигурация;
- протокольные параметры, токены и идентификаторы диалога;
- изменяемые заголовки и данные запросов.
Общий runtime может переиспользовать процессы браузера и другие ресурсы. Но он не должен смешивать изменяемые данные сессий. Некоторые параметры могут применяться только на уровне запуска браузера — в таком случае несовместимые профили необходимо распределять по разным экземплярам.
Допустимо и несколько параллельных браузерных runtime, если это выгоднее для производительности или изоляции конфигураций.
Целевая ёмкость — сотни изолированных сессий. Это пока требование для тестирования, не достигнутый результат.
4. Выбор браузера: Camoufox — основной кандидат, но решение ещё не принято
Пользователь не отвергает Playwright как плохую технологию. Сомнение в том, что стандартный Playwright/Chromium может потребовать значительной дополнительной логики, плагинов или форков, тогда как Camoufox предлагает многое из коробки.
Мы решили провести практическое сравнение, а не выбирать по названию или удобству API.
Кандидаты
A. Camoufox напрямую
Репозиторий: daijro/camoufox.
У проекта есть TypeScript-обвязка, которая управляет модифицированным Firefox и предоставляет Playwright-совместимый API. В проверенной README указаны Camoufox() и NewContext(), настройка идентичности и поддержка отдельных контекстов.
Источник: https://github.com/daijro/camoufox
B. camoufox-js
Отдельная JS-обвязка, не следует путать её с TypeScript-пакетом внутри основного репозитория Camoufox.
Репозиторий: https://github.com/apify/camoufox-js
В ходе исследования были замечены различающиеся версии и ограничения совместимости у разных JS-пакетов. Их нельзя смешивать без проверки API, версий Camoufox и playwright-core.
C. Camofox Browser
Репозиторий: https://github.com/jo-inc/camofox-browser
Это готовый REST-сервис поверх Camoufox. В нём уже реализованы пользовательские сессии, браузерные контексты, управление вкладками, persistence, телеметрия, плагины, ограничения нагрузки и восстановление.
Однако его сервер server.js очень большой — около 7,2 тыс. строк в изученной версии — и содержит много логики, специфичной для браузерного агента: действия с вкладками, DOM snapshots, макросы поиска, загрузки, REST API и другие функции.
Предварительная позиция: Camofox Browser полезен как источник готовых решений по управлению сессиями и восстановлению, но использовать весь сервис как основу не обязательно. Нужно выяснить, можем ли мы взять подходящие механизмы дешевле и без лишней логики.
Что проверять
1. Изоляция cookies, storage, IndexedDB, service workers и состояния идентичности.
2. Стоимость создания сотен контекстов и открытых страниц.
3. Холодный запуск, использование памяти и CPU в простое.
4. Устойчивость при последовательных и параллельных запросах.
5. Сохранение и восстановление авторизации после перезапуска.
6. Доступ к сетевым событиям, возможность получать необходимые запросы и заголовки.
7. Совместимость с реальными сценариями Duck.ai.
8. Возможность прямого HTTP-транспорта после первоначальной браузерной инициализации.
Camoufox — приоритетный кандидат, но выбор должен подтверждаться измерениями.
5. Несколько уровней транспорта
Пользователь согласовал архитектуру с маршрутизацией между несколькими транспортами.
Native HTTP
fetch или undici — основной кандидат для операций, которые не требуют браузерного DOM.
Нужны:
- контроль заголовков на каждый запрос;
- соединения и пулы соединений;
- таймауты и отмена;
- управление proxy;
- отдельные профили сетевого соединения и TLS;
- потоковый ответ.
Browser-native networking
Используется, когда запрос зависит от состояния браузера, JS, service workers, cookies или специфического поведения страницы.
Альтернативный TLS-транспорт
Можно исследовать curl-impersonate или аналог, только если испытания покажут, что стандартного HTTP-клиента недостаточно.
Важно: подмена заголовков не равна изменению TLS ClientHello. Заголовки задаются запросу, а TLS-профиль относится к соединению. Поэтому транспорт должен учитывать совместимость параметров соединения и не смешивать несовместимые профили в одном пуле.
Переход между браузером и HTTP должен быть решением адаптера, а общая инфраструктура должна предоставлять сами механизмы. Если токен устарел или состояние требует восстановления, адаптер может обратиться к браузеру и обновить данные.

- нормальные запросы используют сохранённый контекст и согласованное состояние;

- ошибки challenge, conversation limit и полная блокировка требуют разных стратегий;
- состояние VQD, заголовков, ID диалога и повторов должно принадлежать конкретной сессии.
Эти выводы можно использовать как требования к новому адаптеру. Не нужно переносить старую архитектуру браузера без проверки.

Этот шаг не требует пересборки, не перезапускает существующий стек DuckAI2API и не удаляет Docker-тома.

11. Что пользователь ожидает от работы
Пользователь хочет получить практический результат, а не ещё один многодневный цикл хаотичных исправлений.
Критически важные предпочтения:
- Работать на русском.
- Не выдавать гипотезу за подтверждённый результат.
- Не использовать duckai2api как безусловный эталон и не переносить лишнюю логику.
- Не смешивать незакоммиченные изменения с чистыми рабочими копиями.
- Не использовать один общий build target для нескольких контейнеров.
- Не менять контракт OmniRoute/OmniCopilot ради удобства одного адаптера.
- Не писать новый собственный browser framework, если необходимые механизмы уже есть в подходящей библиотеке.
- При этом не добавлять готовый сервис с тысячами строк кода, если он навязывает ненужную логику.
- Сначала доказать выбор движка и границ компонентов, потом писать runtime и переносить адаптеры.
- Предоставлять точные PowerShell-команды, проверяющие предусловия и прекращающие работу при неожиданном состоянии.
- Не просить пользователя многократно запускать большие диагностические блоки без конкретной цели.
- Код и команды давать обычными Markdown-блоками, не оформлять их как WritingBlock.
- Любое изменение конфигурации делать после понимания исходного состояния, с резервной копией и в изолированном каталоге.
12. Следующие шаги в правильном порядке
1. Исправить и проверить только конфликт имён сервисов в тестовом Compose; убедиться, что проект валидируется.
2. Запустить browser evaluation на 25 сессиях и собрать фактические результаты. Убедиться, что все варианты действительно тестируются и отчёты различают их.
3. На основании результатов выбрать Camoufox напрямую либо готовую обвязку; не принимать решение о сотнях сессий только по документации.
4. Зафиксировать спецификацию Browser Runtime, Session Manager, HTTP Transport, телеметрии и адаптерного контракта.
5. Создать чистую директорию проекта внутри C:\Users\asali\cloudflow, не изменяя старые исходники.
6. Реализовать минимальную общую инфраструктуру и добавить Duck.ai первым адаптером. Переносить только проверенные протокольные алгоритмы и необходимые особенности сайта.
7. Подключить адаптер к OmniRoute без изменения клиентского контракта.
8. Проверить сквозной сценарий в VS Code: сообщение модели → tool_calls → реальное выполнение инструмента → результат обратно модели.
9. Только после этого использовать тот же runtime для следующих адаптеров, например Gemini и GLM.
Главный принцип проекта: чистая целевая архитектура, минимальный необходимый код, повторное использование готовых механизмов там, где это действительно выгодно, и подтверждение каждого существенного решения воспроизводимыми тестами.
